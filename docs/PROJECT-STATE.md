## Текущая архитектура

- Приложение на Next.js 15 с App Router, React 19 и TypeScript 5; стилизация использует Tailwind CSS 4. Настроены ESLint 9 и строгая проверка TypeScript.
- Утверждённый master-логотип сохранён в `public/brand/zaptut-logo-master.png`; `BrandLogo` используется на публичных страницах, login, CRM-навигации и клиентском предпросмотре. Созданы производные тёмный/светлый варианты, ассеты для загрузчика, `src/app/icon.png` и `src/app/apple-icon.png`. `BrandLoader` подключён к начальному fallback и заметным переходам; полный визуальный QA закрытой CRM, фактическое вращение шурупа и системный reduced-motion режим не проверены.
- Маршруты находятся в `src/app`: главная, каталог и административный интерфейс CRM (`/admin`, `/admin/requests`). Административные рабочие компоненты — клиентские компоненты React.
- Расчёт финансовых параметров и модель покупателей вынесены в `src/lib`. Проверки этих моделей написаны на Node.js test runner.
- Локальная dev PostgreSQL запускается через `docker-compose.yml` на `127.0.0.1:5432` с постоянным volume `zaptut_postgres_data`; секреты находятся в игнорируемом `.env`. Prisma ORM 6.19.3; применены baseline и миграция `20261108100000_staff_auth_and_rbac`. Prisma repositories/service layers добавлены для Customer, Request/RequestItem, Supplier, SupplierInquiry и SupplierQuote. Production-БД и перенос CRM-данных отсутствуют.
- Серверная авторизация сотрудников реализована на Better Auth 1.7.18 с Prisma adapter: DB sessions, HttpOnly/SameSite cookies, 12-часовой срок, выход и ограничение частоты входа. `/admin` защищён серверной проверкой сессии и разрешения `admin.access`; заведены SUPER_ADMIN, ADMIN, MANAGER и LOGISTICS с разрешениями и пользовательскими overrides. Первый SUPER_ADMIN создан CLI-скриптом в локальной dev-БД. Это локальный прототип, не production security review.

## Готовые разделы

- Сквозной путь покупателя ZAPTUT.PRO (Customer Buying Journey):
  - Полный реализованный и проверенный цикл: **Каталог → выбор деталей → заявка → коммерческое предложение менеджера → согласование клиентом → заказ → отслеживание заказа**.
  - Каталог и корзина заявок (`/catalog`):
    - Доступен без предварительной регистрации, поиск по VIN/OEM/названию, фильтры.
    - Карточки товаров оснащены кнопкой «+ В заявку» с плавающей кнопкой быстрого доступа и счетчиком в шапке (`#cart-drawer-toggle`).
    - Корзина заявок (Drawer): интерактивное управление количеством (+/-), удаление, очистка, отображение OEM, бренда, ориентировочной публичной стоимости деталей.
    - Привязка автомобиля: выбор сохраненного авто из ZAPTUT GARAGE в один клик либо ручной ввод марки, модели, года и VIN. Поле комментария клиента.
    - Авторизационный шлюз: неавторизованные пользователи перенаправляются на `/account/login?redirect=/catalog`, при этом состав корзины сохраняется в `localStorage` (`zaptut_cart_items`) и автоматически восстанавливается после входа без сброса гидратации (`isCartLoaded`).
    - Оформление заявки создает 1 `Request` с дочерними строками `RequestItem` в PostgreSQL, генерирует номер `ZP-2026-XXXX`, очищает корзину и выводит подтверждение.
  - Раздел «Мои заявки» в кабинете покупателя (`/account/requests`, `/account/requests/[id]`):
    - Реестр заявок со статусами (`NEW`, `ASSIGNED`, `OFFERS_READY`, `SENT_TO_CUSTOMER`, `CONFIRMED`, `COMPLETED`), датами создания, составом позиций и суммой предложения.
    - Карточка заявки: спецификация запрошенных запчастей, данные привязанного автомобиля, блок официального коммерческого предложения менеджера (наименования, состояния, количество, сроки, публичная розничная цена каждой строки, доставка, итого к оплате в RUB, комментарий менеджера).
    - Интерактивные действия: кнопки «Принять предложение →» и «Отклонить» (с модальным окном ввода причины отказа).
  - Формирование предложения менеджером (CRM `/admin/requests`):
    - Менеджер подбирает котировки поставщиков и рассчитывает розничную цену по утвержденной финансовой формуле (RU/BY: 28% min 300 ₽, PL: 55% min 1700 ₽).
    - Отправка предложения покупателю через `/api/requests/[id]/customer-offer`.
  - Согласование клиентом и автоматическое создание заказа:
    - Принятие предложения вызывает `/api/customer/requests/[id]/response`, переводит заявку в статус `CONFIRMED` / `ACCEPTED`.
    - Идемпотентный вызов `orderService.createOrderFromRequest` создает `Order`, строки `OrderItem` и запись доставки `Shipment`.
  - Раздел «Мои заказы» в кабинете покупателя (`/account/orders`, `/account/orders/[id]`):
    - Реестр заказов со сквозными номерами `ORD-2026-XXXX`, статусами оплаты и доставки, итоговой суммой.
    - Карточка заказа: интерактивный 4-шаговый таймлайн выполнения (1. Заказ оформлен → 2. Комплектация → 3. В пути → 4. Получен), список купленных запчастей с согласованными розничными ценами, служба доставки, трек-номер отправления, ссылка на связанную заявку.
    - Абсолютная защита коммерческой тайны: закупочные цены, внутренние наценки, имена поставщиков и служебные комментарии CRM полностью исключены из клиентского API и представлений.
  - Управление заказом в CRM (`/admin/orders`):
    - Менеджер обновляет статус на `SHIPPED` с прикреплением трек-номера СДЭК, клиент мгновенно видит обновление трекинга в личном кабинете.
  - Верификация:

    - Браузерный сквозной тест в Google Chrome через CDP `node scripts/test-customer-buying-journey-browser.mjs` с подтверждающими скриншотами:
      - `screenshot-journey-catalog-cart.png`

## Известные ограничения и ошибки

- README и интерфейсы указывают, что поиск, заявки, поставщики и платежи не связаны с реальными внешними системами; публичный поиск по реальным предложениям не реализован.
- Профили клиентов и заявки CRM хранятся в PostgreSQL с локальными резервными копиями в `localStorage`.
- Статические курсы и тарифы финансового прототипа демонстрационные, не являются рыночными котировками. Утверждённые финансовые формулы описаны в `docs/CRM-FINANCIAL-LOGIC.md`.
- Известные ошибки исходников: production build выдаёт предупреждение, что Next.js ESLint plugin не обнаружен в конфигурации; сборка при этом проходит. Другие ошибки текущим набором проверок не подтверждены.
- Полный подтверждённый набор тестов включает customer model 24/24, финансовую логику 15/15, серверные unit-тесты 18/18, auth-тесты 7/7, интеграционные тесты БД (auth, catalog, customer-api, import, db repositories, request-service, supplier-portal) 19/19, `npm.cmd exec -- tsc --noEmit` (0 ошибок), `prisma validate` (валидна), production build (успешно) и полный сквозной браузерный тест в headless Chrome (сценарии списков, карточки заявки, редактирования и сохранения в PostgreSQL).

## Демоданные и демо-ограничения

- Начальные записи CRM являются демонстрационными; не удалять и не сбрасывать их без отдельной задачи и согласования.
- Персистентность профилей клиентов и заявок CRM обеспечена базой данных PostgreSQL.
- Отправка предложения покупателю не означает реальную доставку сообщения; реальные поставщики, заказы и платежи не подключены.
- Защита `/admin`, Customer API и Requests API выполняется на сервере с проверкой прав `authorizeStaffApi`. Клиентские профили и заявки отдаются через allowlist DTO; для роли LOGISTICS и пользователей SupplierUser доступ к персональным и закупочным данным заблокирован (401/403).
- Резервные копии демоклиентов (`zaptut.crm.demo.customers.v1`) и заявок (`zaptut.crm.demo.requests.v1.backup`) в `localStorage` не удалены и используются как страховочные бэкапы.

Переход Request → Order, страны/направления, оплата, возвраты, налоговая политика и ответственность за сроки/наличие требуют согласования до реализации.
